    AI API 在企業 Workflow 中的角色（案例教學：含雲端 LLM 實務選型）

    AI Workflow 實務案例 ⏱️ 閱讀時間 8 分鐘

    💡 本章定位與觀念解析

    本章核心目的在於讓大家建立真正的 AI Native 觀念：
    「AI API 在企業系統中，通常只是 Workflow 中的一個智慧節點（Intelligence Node），而不是整個系統！」

    一、案例一：OCR 文件自動建立 ERP 資料（雙版本 Workflow 與雲端 LLM 實務舉例）

    【實務情境】 使用者上傳一張發票、報價單或採購單，希望系統自動解析並正確寫入銀河軟體 內部的資料庫。

    👁️ 節點 1：PaddleOCR (雲端 OCR 地端替代方案)

    完美替代昂貴的雲端 OCR！開源免費、高精度繁體中文與表格辨識，地端秒級提取文字，完全零 API 費用。

    🤖 節點 2：Qwen / Qwen2.5-VL (開源多模態 LLM)

    頂級開源視覺語言模型，看圖與文字理解媲美雲端大模型，精準轉譯並輸出銀河軟體 寫入格式 JSON。

    ⚡ 節點 3：vLLM (地端高吞吐推理引擎)

    採用 PagedAttention 記憶體最佳化，將 Qwen 地端 GPU 叫用吞吐量拉高 2~4 倍，實現高併發穩定回應！

    二、標準案例分析與雲端選型評估

    1. 使用者做了什麼？

    使用者只需在前端 Web 介面 (HTML UI) 上傳發票或單據圖片，無須人工手動輸入數十個欄位。

    2. Workflow 如何運作？

    前端接收圖檔後呼叫後端 API 觸發 Workflow 流程，經由雲端 AI API 處理後產出標準 JSON，通過後端邏輯與 Rule 驗證後自動寫入 ERP 資料庫。

    3. AI API 在哪一個節點發揮作用？（具體雲端服務舉例）

    在版本一（能力分工版）中：

    • OCR 節點： 採用 Azure AI Document Intelligence 或 Google Cloud Vision，精準抽取表單座標與文字。
    • LLM 節點： 將抽取後的文字送給極低成本且高速的雲端文字 LLM，如 OpenAI gpt-4o-mini、Claude 3.5 Haiku 或 DeepSeek Chat，設定 response_format: {"type": "json_object"} 進行欄位轉譯。

    在版本二（多模態一步到位版）中：

    • 直接將圖片以 Base64 或 URL 送入具備 Vision 能力的雲端多模態模型，如 Google Gemini 1.5 Flash、OpenAI gpt-4o 或 Claude 3.5 Sonnet，由單一模型一步到位回傳完整的 ERP 寫入 JSON。
    4. 為什麼要這樣設計？（版本一能力分工的理由）
    • 🎯 極致成本優勢：專業 OCR 辨識費用極低，搭配 gpt-4o-mini 或 DeepSeek 處理純文字 Token，費用僅為多模態 Vision LLM 的幾十分之一。
    • 🔄 靈活模組替換：若哪天有更划算的新文字模型，只需更換節點 2，前端與 OCR 節點完全不受影響。
    • 🛠️ 故障排除 (Debugging)：能精確知道是 OCR 漏字，還是 LLM 欄位對應錯誤。
    5. 是否還有其他設計方式？（版本二多模態的理由）

    版本二採用 Gemini 1.5 Flash 等多模態模型，優點在於無須串接與維護多個 API，程式碼最短，適合快速驗證 POC 與複雜非標準手寫單據。

    6. 雲端 OCR 替代方案與地端私有化（版本三地端開源 AI 組合理由）

    當企業追求極致省錢（尋求昂貴雲端 OCR 的替代方案）、極度嚴苛的資安限制（敏感單據絕對不上雲），或每日有數萬張龐大單據處理量時，版本三是最佳實戰解法：

    • 採用 PaddleOCR 完美替代昂貴的雲端 OCR，在地端伺服器極速提取單據文字。
    • 搭配地端開源視覺語言模型 Qwen / Qwen2.5-VL 與 vLLM 高吞吐推理引擎，0 API 營運費用、資料 100% 留在企業地端，實現極致私有化與高併發吞吐量！

    三、本案例希望學員理解的核心心法

    企業專案沒有標準答案！有時候我們會將 AI 能力拆分合作，有時候會使用一個多模態模型一次完成。

    ⚖️ 選擇 Workflow 設計時的 7 大衡量維度：
    1. 💰 成本 (Cost)：Token 與 API 費用是否符合預算（例如 gpt-4o-mini vs gpt-4o Vision）。
    2. 🎯 準確率 (Accuracy)：辨識與欄位對應的精準度。
    3. 🛠️ 維護性 (Maintainability)：錯誤發生時是否方便除錯。
    4. 🔄 可替換性 (Flexibility)：是否容易無痛切換供應商。
    5. ⚡ 執行速度 (Latency)：整體 Workflow 處理耗時。
    6. 📋 專案需求 (Requirements)：客戶即時性或批次處理規範。
    7. 🚀 未來擴充性 (Scalability)：是否能輕易支援更多單據種類。

    👉 結論：AI Workflow 沒有唯一解。重點不是使用了幾個 AI，而是是否為這個專案設計出最適合的 Workflow！

    四、本章總結觀念收斂

    「 不要認為 AI API 就是一個很龐大複雜的系統。
    AI API 是企業 Workflow 中的一個『能力節點（Capability Node）』，可以依需求拆分，也可以整合。」

    「未來企業真正設計的，不只是 Workflow，而是 AI Workflow！
    真正需要思考的，不是盲目追求最新模型，而是：每一個 AI 能力（OpenAI, Gemini, Claude, DeepSeek, Azure），應該放在 Workflow 的哪一個位置，才能達到最佳成本、效率與準確率！」
